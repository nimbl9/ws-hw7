# Ответы на теоретические вопросы — Самостоятельная работа студентов / СРС (Модуль 07)

## 1. Что такое аутентификация и авторизация?
- **Аутентификация (Authentication)** — этап подтверждения подлинности субъекта (пользователя или сервиса), обращающегося к системе. Система сверяет предъявленные учетные данные (логин/пароль, токен, сертификат) с доверенными записями.
- **Авторизация (Authorization)** — этап разграничения прав и проверки полномочий проверенного субъекта. Система определяет, разрешено ли пользователю выполнить конкретную операцию (чтение, добавление, изменение, удаление) над конкретным ресурсом.

## 2. Как работает Basic Authentication?
Клиент соединяет имя пользователя и пароль через двоеточие (`username:password`) и кодирует полученную строку в представление Base64. Данная строка передается в HTTP-заголовке:
`Authorization: Basic <base64_encoded_string>`
Сервер принимает входящий запрос, извлекает и декодирует заголовок, валидирует учетные данные через локальную базу или сервис пользователей и в случае совпадения формирует контекст безопасности (`ClaimsPrincipal`). Если заголовок отсутствует или данные неверны, сервер возвращает статус `401 Unauthorized`.

## 3. Для чего используются интерфейсы IIdentity и IPrincipal?
- `IIdentity` инкапсулирует данные о личности пользователя. Содержит свойства `Name` (имя пользователя), `AuthenticationType` (тип механизма проверки, например `"Basic"`) и `IsAuthenticated` (флаг успешного прохождения проверки подлинности).
- `IPrincipal` представляет полный контекст безопасности пользователя, в контексте которого выполняется поток или запрос. Содержит свойство `Identity` и метод `IsInRole(string role)` для проверки принадлежности пользователя к определенной роли безопасности.

## 4. Что такое Claims и для чего они необходимы?
**Claim (утверждение)** — это единица информации о пользователе в формате «тип-значение» (`Type` и `Value`), выданная доверенным источником (эмитентом). Утверждениями могут быть: имя (`Name`), идентификатор (`NameIdentifier`), email (`Email`), роли (`Role`), дата рождения, отдел, должность и любые другие атрибуты. В отличие от жесткой привязки к фиксированным полям БД, модель Claims позволяет гибко строить детализированные политики доступа (Claims-based Authorization) и расширять модель пользователя без изменения интерфейсов безопасности.

## 5. Чем отличаются ClaimsIdentity и ClaimsPrincipal?
- `ClaimsIdentity` — это удостоверение (паспорт) пользователя, состоящее из списка утверждений (`Claim`). У одного пользователя может быть несколько разных удостоверений (например, удостоверение Active Directory и удостоверение Google).
- `ClaimsPrincipal` — это субъект (сам пользователь), владеющий одним или несколькими удостоверениями `ClaimsIdentity`. Свойство `HttpContext.User` в ASP.NET Core является экземпляром `ClaimsPrincipal`, через который приложение получает доступ ко всем объединенным удостоверениям и их утверждениям.

## 6. Как работает атрибут [Authorize]?
Атрибут `[Authorize]` в ASP.NET Core реализует интерфейс фильтра авторизации. При поступлении HTTP-запроса фильтр проверяет:
1. Прошел ли пользователь аутентификацию (`User.Identity.IsAuthenticated == true`). Если нет, запрос прерывается с кодом `401 Unauthorized`.
2. Если в атрибуте указаны роли (например, `[Authorize(Roles = "Admin,Teacher")]`) или политики (`Policy`), фильтр проверяет соответствие текущего пользователя заданным условиям. Если условия не соблюдены, возвращается статус `403 Forbidden`.

## 7. Для чего используется [AllowAnonymous]?
Атрибут `[AllowAnonymous]` служит для явного отключения проверок авторизации и аутентификации для конкретного метода действия (action), когда на уровне всего контроллера установлен защитный атрибут (например, `[Authorize]` или пользовательский `[BasicAuthentication]`). Это позволяет открыть публичный доступ к отдельным конечным точкам (например, `/api/courses/info` или страница входа), не снимая защиту с остальных методов контроллера.

## 8. Чем отличаются HTTP-коды 401 Unauthorized и 403 Forbidden?
- **401 Unauthorized (Не авторизован / Требуется аутентификация)**: сервер указывает, что для доступа к ресурсу необходимо подтвердить свою личность. Возвращается, когда заголовок авторизации отсутствует, искажен или содержит неверный пароль.
- **403 Forbidden (Запрещено / Доступ запрещен)**: сервер успешно установил личность пользователя, однако у данного пользователя недостаточно прав доступа (ролей) для запрошенного действия. Повторная отправка тех же учетных данных не решит проблему.

## 9. Какие недостатки имеет Basic Authentication?
1. **Слабая защищенность учетных данных**: кодирование Base64 не является шифрованием, данные легко читаются любым перехватчиком при отсутствии TLS/HTTPS.
2. **Передача учетных данных при каждом запросе**: повышается риск компрометации пароля при перехвате трафика.
3. **Отсутствие времени жизни (expiry)**: нет механизма автоматического истечения сессии, как у токенов JWT или сессионных cookie.
4. **Сложность безопасного выхода (Logout)**: большинство браузеров кэшируют учетные данные Basic Auth до полного закрытия окна браузера, делая нормальный логаут затруднительным.

## 10. Почему для передачи учётных данных необходимо использовать HTTPS?
Протокол HTTPS использует криптографический протокол TLS/SSL для шифрования всего канала связи между клиентом и сервером. В зашифрованный конверт попадают URL, заголовки (включая заголовок `Authorization: Basic ...`) и тело HTTP-пакета. Без HTTPS учетные данные передаются по открытым каналам в виде открытого текста (декодируемого из Base64), что делает их легкой добычей для атак «человек посередине» (Man-in-the-Middle) и снифферов трафика в локальных сетях и точках Wi-Fi.
